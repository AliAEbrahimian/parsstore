--------------------------------------------------------------------------------
1. Scope and product decisions
--------------------------------------------------------------------------------

ParsStore is an informational site, not an online shop. There is no shopping
cart, no checkout and no public user account. Visitors can:

  * browse the home page sections and a full catalogue at /products/;
  * open part detail pages at /products/<id>/;
  * submit a price inquiry (stored as an Inquiry row);
  * apply for the customer club (stored as a Customer row).

Prices and stock are confirmed by phone or email. The club discount is applied
to an offline or telephone proforma invoice, not in a web checkout.

Data is split deliberately:

  * Static marketing copy (brands, categories, features, FAQ, club tiers) is
    Python data in core/content.py. Editing text needs no migration.
  * Products, specifications, inquiries and club members live in SQLite and are
    managed from the Django admin.
  * All user-facing strings (labels, messages, emails, admin actions) are in
    core/i18n.py, with English and German values.

2. Quick start (local development)
--------------------------------------------------------------------------------

  python -m venv .venv
  .venv\Scripts\activate          # Windows
  # source .venv/bin/activate     # macOS / Linux

  pip install -r requirements.txt
  cp .env.example .env
  # In .env set DJANGO_DEBUG=1 and a local DJANGO_SECRET_KEY.

  python manage.py migrate
  python manage.py createsuperuser
  python manage.py runserver

Open http://127.0.0.1:8000. The admin lives at /admin/ unless DJANGO_ADMIN_PATH
is changed. The .env file, db.sqlite3, media/ and staticfiles/ are gitignored.

Verification commands:

  python manage.py check
  python manage.py makemigrations --check --dry-run
  python manage.py test
  python manage.py check --deploy   # with production-like variables (section 9)

3. Architecture at a glance
--------------------------------------------------------------------------------

Request path:

  browser
    -> SecurityMiddleware / SessionMiddleware
    -> core.middleware.SecurityHeadersMiddleware
    -> core.middleware.LanguageMiddleware        (sets ?lang= / cookie language)
    -> URL resolution (parsstore/urls.py, core/urls.py)
    -> view (core/views.py)                       (query, form handling, email)
    -> context processor (core/context_processors.py) adds LANG, T, SITE, NAV,
       LANGUAGES, SWITCH_URLS, BRANDS_FOOTER
    -> template (core/templates/core/*.html)
    -> response with CSP, Permissions-Policy and Content-Language headers

Language model:

  * Only two language codes exist: en (default) and de.
  * core/i18n.py defines LANGUAGES and DEFAULT_LANGUAGE = "en".
  * The short helper _(en, de) returns {"en": ..., "de": ...}.
  * t(key) and flat(lang) read from the UI dictionary; get_content(lang) in
    core/content_i18n.py returns the display content for the active language.
  * LanguageMiddleware accepts ?lang=en|de, remembers the choice in the
    parsstore_lang cookie for one year, and activates Django translations.
  * Unsupported values fall back to English. All pages render dir="ltr".
  * The language switcher keeps the current path and all non-language query
    parameters, so search results and filters survive a language change.

5. Modules in detail
--------------------------------------------------------------------------------

5.1 parsstore/settings.py
  A tiny .env parser loads KEY=VALUE pairs without any third-party package.
  env_bool(), env_int() and env_list() convert values with safe defaults.
  DEBUG defaults to False. When DEBUG is False, DJANGO_SECRET_KEY is required.
  Language configuration is LANGUAGE_CODE="en" and LANGUAGES = en, de.
  The admin slug comes from DJANGO_ADMIN_PATH and is not hard-coded.
  Cache selection: Redis backend when DJANGO_CACHE_BACKEND or DJANGO_REDIS_URL
  is set, otherwise LocMemCache (local development only).
  Security settings are applied in the `if not DEBUG` block; proxy headers are
  trusted only when DJANGO_BEHIND_PROXY / DJANGO_TRUST_PROXY_HEADERS are set.

5.2 core/models.py
  Inquiry: name, company, phone, email, machine, message, created_at,
           is_processed. Used by the contact form.
  Product: name, brand, machine_models, category, summary, description, image,
           generated image_thumb, image_alt, flags and sort_order. Includes
           database indexes for active/featured/sort ordering, category and
           brand. save() builds a WebP thumbnail and deletes replaced files
           with transaction.on_commit().
  ProductSpec: label, value, sort_order; related to Product via `specs`.
  Customer: membership code, name, contact data, tier, discount_percent,
            status, notes and timestamps. A unique, readable PT- code is
            generated on save with collision retry. Phone numbers are cleaned
            and localised digits normalised before the uniqueness check.

5.3 core/content.py and core/content_i18n.py
  content.py holds the English source dictionaries SITE, BRANDS, CATEGORIES,
  FEATURES, STATS, STEPS, CLUB and FAQ. content_i18n.py holds German overrides
  in _DE and get_content(lang): English is deep-copied as the base, German
  replaces translated fields while inheriting shared values such as links and
  phone numbers. Change demo text here, not in templates.

5.4 core/i18n.py
  UI contains every visible label and message as _(english, german). Helpers:
    current_language()  active code, validated against LANGUAGES
    t(key, lang=None)   one translated string
    flat(lang=None)     all strings as a flat dict for templates
  To add text: add a key with both translations, then use {{ T.key }} in a
  template or t("key") in Python.

5.5 core/middleware.py
  SecurityHeadersMiddleware sets a strict CSP (default-src 'self', no inline
  scripts, no remote origins), Permissions-Policy, and leaves Django's other
  security headers in place. LanguageMiddleware resolves the language from
  ?lang=, then the cookie, then the default, activates it with
  django.utils.translation.activate(), sets Content-Language, and writes the
  cookie when requested.

5.6 core/context_processors.py
  Provides every template with LANG, LANGUAGES, T, SITE, NAV, BRANDS_FOOTER
  and SWITCH_URLS. Navigation links include the active language and home
  anchors. Switch URLs preserve non-language GET parameters.

5.7 core/views.py
  home(): renders the landing page, handles both POST forms with rate limits,
          emails and messages, and prefills the inquiry box from ?product=<id>.
  product_list(): validates q/category/brand, filters active products,
                  paginates with Paginator and builds elided page links.
  product_detail(): shows one active product, its specs and related parts.
  Error handlers render core/404.html and core/500.html.
  Private helpers handle IP selection (opt-in X-Forwarded-For), atomic cache
  counters, safe email sending, recipient resolution and notification bodies.

5.8 core/forms.py
  HoneypotMixin rejects filled hidden fields. InquiryForm and ClubSignupForm
  set translated labels/placeholders, strip whitespace, clean phone numbers,
  validate message length and use the active-language duplicate-phone message.

5.9 core/images.py and core/utils.py
  make_thumbnail() opens an uploaded image, applies EXIF orientation, flattens
  transparency on white, and saves a WebP of at most 960x960 with quality 82.
  normalize_digits() maps non-Latin digits to ASCII; phone_digits() keeps only
  digits, giving a consistent, comparable phone number format.

5.10 core/admin.py
  Product admin: searchable/filterable list, spec inline, image preview,
  rebuild-thumbnails action. Customer admin: tier/status editing and activate
  / block actions. Action messages are translated through i18n.py.

5.11 Templates, CSS and JavaScript
  base.html defines the LTR document shell, header switcher, theme buttons,
  navigation, footer, WhatsApp button and message area. home.html contains the
  anchored sections; products.html and product_detail.html cover the catalogue.
  style.css implements dark/light/auto themes and responsive layouts with local
  assets only. theme.js runs synchronously in <head> to avoid a colour flash.
  main.js handles the mobile menu, scroll effects, reveal animations, inquiry
  prefill and dismissible messages.

7. Forms, email and rate limiting
--------------------------------------------------------------------------------

Inquiry POST:
  1. Honeypot and rate limit checked.
  2. InquiryForm validated; localised phone digits normalised.
  3. Inquiry saved; admin notification and customer confirmation sent through
     _send_mail_safely(), which logs SMTP errors without losing the form data.
  4. Translated success/error message, redirect to /?lang=<code>#contact.

Club POST:
  Same flow with CLUB_* limits, a pending Customer, a generated code, and a
  redirect to /?lang=<code>#club. Admin activation sets status to active.

Rate limiting uses cache.add() + cache.incr(), which is atomic. With multiple
workers, configure Redis; LocMemCache would give each worker its own counter.
TRUST_PROXY_HEADERS must be enabled only behind a proxy you control.

--------------------------------------------------------------------------------
8. Security controls
--------------------------------------------------------------------------------

  * DEBUG defaults to False and a secret key is mandatory outside debug.
  * Strict CSP: only self-hosted assets, no inline scripts, form-action self.
  * Permissions-Policy and Django security middleware are enabled.
  * CSRF protection on every POST; hidden honeypot fields on both forms.
  * Server-side validation for all input; GET filters are length-limited and
    validated against known category/brand values.
  * Per-IP atomic throttling for inquiries and club signups.
  * X-Forwarded-For is ignored unless explicitly trusted.
  * Uploaded images are processed by Pillow; thumbnails are regenerated and old
    files removed only after the database transaction commits.
  * Configurable admin path; no public accounts or payment flow.
  * check --deploy is part of CI.

9. Production deployment checklist
--------------------------------------------------------------------------------

 1. Use PostgreSQL (recommended) or a managed SQLite volume; set DJANGO_DB_PATH.
 2. Set DEBUG=0, a random 50+ character DJANGO_SECRET_KEY, real
    DJANGO_ALLOWED_HOSTS and DJANGO_CSRF_TRUSTED_ORIGINS.
 3. Enable HTTPS settings: SECURE_SSL_REDIRECT, secure cookies and HSTS. Set
    DJANGO_BEHIND_PROXY if traffic arrives through a trusted proxy.
 4. Configure a shared Redis cache via DJANGO_REDIS_URL when running more than
    one worker.
 5. Run: python manage.py migrate
          python manage.py collectstatic --noinput
 6. Serve staticfiles/ and media/ with Nginx; deny script execution in media/.
 7. Run Gunicorn/uvicorn behind HTTPS. Keep the admin path secret.
 8. Set SMTP variables and notification recipients; test both email flows.
 9. Back up the database, media/ and the .env file separately.
10. Run python manage.py check --deploy before going live.

Example deploy check:

  DJANGO_DEBUG=0 \
  DJANGO_SECRET_KEY="<random-50+-character-key>" \
  DJANGO_ALLOWED_HOSTS="example.com" \
  DJANGO_SECURE_SSL_REDIRECT=1 \
  DJANGO_SECURE_HSTS_SECONDS=31536000 \
  DJANGO_SECURE_HSTS_PRELOAD=1 \
  python manage.py check --deploy

--------------------------------------------------------------------------------
10. Customisation guide
--------------------------------------------------------------------------------

Change company details: edit SITE in core/content.py and its German override
in core/content_i18n.py.
Change brands/categories/FAQ: edit BRANDS, CATEGORIES, FAQ in both files.
Change labels or emails: add/update the key in core/i18n.py for both languages.
Add a language: extend LANGUAGES in i18n.py and settings.py, add a third value
to _(), add content overrides, then update tests and templates.
Add a product or member: use the Django admin at /admin/.

--------------------------------------------------------------------------------
11. Known limitations
--------------------------------------------------------------------------------

  * No online checkout, inventory sync or payment gateway (by design).
  * SQLite is suitable for development/small deployments; use PostgreSQL for
    heavier traffic.
  * LocMemCache is per-process; use Redis for consistent rate limits.
  * Content is static Python data; changing it requires a code deployment.
  * demo phone numbers, email and address are placeholders.
