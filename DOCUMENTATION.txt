================================================================================
۰. این فایل چیست
================================================================================
DOCUMENTATION.txt یک سند «منبع حقیقت» برای پروژه است و شامل این موارد می‌شود:

- فهرست دقیق همهٔ فایل‌ها و نقش هرکدام.
- توضیح خط‌به‌خط یا بلوک‌به‌بلوک کدهای پایتون.
- توضیح ساختار قالب‌ها، شناسه‌ها و کلاس‌های CSS.
- توضیح رفتار جاوااسکریپت (منوی موبایل، انیمیشن، پیام‌ها و انتخاب تم).
- فهرست کامل تنظیمات محیطی و مقادیر پیش‌فرض.
- اقدامات امنیتی و تحلیل تهدیدهای باقی‌مانده.
- نتایج واقعی آزمون‌ها، بررسی مرورگر و پیشنهادهای استقرار.

نکته: این پروژه «بروشور آنلاین» است، نه فروشگاه اینترنتی. هیچ سبد خرید،
درگاه پرداخت یا حساب کاربری عمومی وجود ندارد. نوشتن در پایگاه‌داده فقط از سه
راه انجام می‌شود: ثبت فرم «استعلام قیمت»، ثبت «درخواست عضویت باشگاه» و
مدیریت محصولات/اعضا از پنل ادمین. از نسخهٔ 1.3.0 کاتالوگ کامل در صفحهٔ
جداگانهٔ /products/ و صفحهٔ جزئیات هر قطعه در /products/&lt;id&gt;/ است؛ صفحهٔ
اصلی فقط چند قطعهٔ منتخب را نشان می‌دهد. تخفیف باشگاه هنگام خرید حضوری یا تلفنی
اعمال می‌شود، نه در یک سبد خرید آنلاین.

================================================================================
۱. شناسنامه و تصمیم‌های معماری
================================================================================
۱.۱ چرا این ساختار؟
- «صفحهٔ اصلی تک‌صفحه‌ای»: بخش‌های معرفی در یک قالب (home.html) با لنگرهای
  #about ، #products ، #brands ، #why ، #faq ، #club و #contact جمع شده‌اند
  تا ناوبری سریع باشد، اما کاتالوگ کامل به صفحهٔ مستقل /products/ منتقل شده
  است. صفحهٔ اصلی فقط PRODUCTS_HOME_LIMIT قطعهٔ منتخب را نشان می‌دهد؛ نمایش
  هم‌زمان ۸۰۰ تا ۱۲۰۰ قطعه در یک صفحه نه برای کاربر قابل مرور است و نه برای
  پاسخ سرور بهینه.
- «کاتالوگ صفحه‌بندی‌شده به‌جای فهرست یک‌جا»: ویو product_list با
  Paginator جنگو هر بار فقط PRODUCTS_PAGE_SIZE قطعه (پیش‌فرض ۲۴) می‌خواند؛
  جست‌وجو و فیلترها روی همان کوئری اعمال می‌شوند و شمارش کل با count انجام
  می‌شود. صفحهٔ جزئیات همهٔ مشخصات یک قطعه را نشان می‌دهد تا کارت‌های کوچک
  شلوغ نشوند.
- «ایندکس برای رشد کاتالوگ»: سه ایندکس روی Product (فعال/منتخب/ترتیب، دسته و
  برند) اضافه شده تا فیلتر و مرتب‌سازی با ۸۰۰ تا ۱۲۰۰ ردیف هم سریع بماند.
- «محتوای ثابت بدون پایگاه‌داده»: متن‌ها، برندها، آمار و سؤالات در
  core/content.py هستند. مزیت: ویرایش بدون پنل، سرعت بالا، عدم نیاز به مهاجرت
  برای تغییر متن. از نسخهٔ 1.2.0 محصولات و اعضای باشگاه در پایگاه‌داده‌اند،
  چون باید از پنل ادمین اضافه/ویرایش شوند.
- «چهار مدل کوچک»: Inquiry (استعلام)، Product + ProductSpec (کاتالوگ و مشخصات)
  و Customer (باشگاه). هیچ جدول سفارش، سبد خرید یا پرداخت وجود ندارد.
- «تصویر سبک و سریع»: تصویر اصلی محصول نگه داشته می‌شود، ولی هنگام ذخیره یک
  بندانگشتی WebP (حداکثر ۹۶۰×۹۶۰) ساخته می‌شود و قالب همان را با
  loading="lazy" و ابعاد مشخص نمایش می‌دهد. نتیجه: بدون تأخیر محسوس و بدون
  ارسال فایل چندمگابایتی به موبایل.
- «بدون CDN»: فونت وزیرمتن و آیکون‌ها محلی هستند. به همین دلیل CSP می‌تواند
  کاملاً سخت‌گیرانه باشد و سایت در شبکهٔ محدود/فیلترشده هم کار کند.
- «رنگ‌بندی صنعتی + کهربایی»: پس‌زمینهٔ تیرهٔ #080b0e و رنگ تأکیدی #eda33f،
  مناسب فضای صنعتی و خوانایی بالا. از نسخهٔ 1.1.0 یک پالت روشن کاغذی
  (#f6f3ee) هم وجود دارد و کاربر می‌تواند بین تاریک، روشن و خودکار انتخاب کند.
- «تم بدون پرش رنگ»: theme.js در <head> و پیش از رنگ‌آمیزی اجرا می‌شود؛
  انتخاب کاربر در localStorage می‌ماند و حالت خودکار ترجیح سیستم را دنبال می‌کند.

================================================================================
۵. جریان یک درخواست از مرورگر تا پاسخ
================================================================================
GET /
  1) SecurityMiddleware → هدرهای امنیتی پایه
  2) SessionMiddleware → نشست (برای پیام‌های flash)
  3) CommonMiddleware → مسیرها/اسلش
  4) CsrfMiddleware → آماده‌سازی توکن
  5) AuthenticationMiddleware → کاربر (فقط برای ادمین مهم است)
  6) MessageMiddleware → پشتیبانی پیام‌ها
  7) XFrameOptionsMiddleware → X-Frame-Options: DENY
  8) core.middleware.SecurityHeadersMiddleware → CSP و Permissions-Policy
  9) URL resolver → core.urls → views.home
 10) home() → _inquiry_prefill (اختیاری از ?product=) + هر دو فرم + context
 11) Product.objects.filter(is_active=True) با prefetch_related("specs") و
     محدودیت PRODUCTS_HOME_LIMIT (پیش‌فرض ۶) و شمارش کل فعال‌ها
 12) render("core/home.html") → base.html + home.html + context_processors
 13) پاسخ HTML (۲۰۰) + هدرهای امنیتی

GET /products/  (کاتالوگ)
  1) همان زنجیرهٔ میدل‌ور تا URL resolver
  2) core.urls → views.product_list
  3) اعتبارسنجی q/category/brand؛ ساخت فهرست برندهای فعال
  4) Product.objects.filter(is_active=True).prefetch_related("specs") +
     جست‌وجوی icontains + فیلتر دسته/برند + ترتیب منتخب‌ها
  5) Paginator(products, PRODUCTS_PAGE_SIZE محدود به ۶ تا ۹۶)
     → get_page(request.GET["page"]) و شمارش کل
  6) render("core/products.html") → کارت‌ها + صفحه‌بندی

GET /products/<id>/  (جزئیات)
  1) core.urls → views.product_detail
  2) get_object_or_404 روی Product فعال با prefetch_related("specs")
  3) حداکثر ۴ قطعهٔ فعال هم‌دسته به‌عنوان related
  4) render("core/product_detail.html") + دکمهٔ استعلام با ?product=<id>#contact

POST / (فرم استعلام)

خطوط 14-25 ثابت CSP:
  - default-src 'self' → پیش‌فرض همهٔ منابع فقط از همان دامنه.
  - base-uri 'self' → جلوگیری از تغییر base tag.
  - connect-src 'self' → fetch/XHR فقط به خود سایت.
  - font-src 'self' → فونت محلی.
  - form-action 'self' → فرم فقط به خود سایت (ضد ارسال به دامنهٔ مهاجم).
  - frame-ancestors 'none' → ضد iframe (هم‌راستا با X-Frame-Options).
  - img-src 'self' data: → تصاویر محلی و data URI (فاوآیکون/آینده).
  - object-src 'none' → غیرفعال‌کردن pluginها (Flash/Java).
  - script-src 'self' → فقط اسکریپت‌های محلی main.js و theme.js؛ هیچ inline
            script اجرا نمی‌شود.
  - style-src 'self' → فقط style.css محلی؛ هیچ style attribute در HTML نیست.

خطوط 27-29 Permissions-Policy: غیرفعال‌کردن دوربین، میکروفن، موقعیت، پرداخت و USB.

خطوط 31-32 سازندهٔ middleware: ذخیرهٔ get_response (قرارداد جنگو).

    Permissions-Policy، Referrer-Policy (از SECURE_REFERRER_POLICY) و nosniff.

    تا تنظیمات صریح جنگو بازنویسی نشود.

در <head> به‌صورت همگام بارگذاری می‌شود؛ بنابراین پیش از نخستین رنگ‌آمیزی بدن،
ویژگی‌های <html> را تنظیم می‌کند و پرش رنگ (FOUC) رخ نمی‌دهد.

خطوط 1-4   توضیح فارسی: هدف، دلیل بارگذاری همگام و دلیل نبود کد inline.
خط 5       IIFE با "use strict" → جلوگیری از آلودگی scope globale.
خط 8       STORAGE_KEY = "parstextile.theme" (کلید localStorage).
خط 9       MODES = ["dark", "light", "auto"] (اعتبارسنجی مقدار ذخیره‌شده).
خط 10      root = document.documentElement.
خطوط 12-14 systemLight: matchMedia("(prefers-color-scheme: light)") با
           بررسی وجود matchMedia (محیط‌های قدیمی).

خطوط 16-24 readMode:
  - خواندن localStorage در try/catch (حالت خصوصی ممکن است مسدود باشد).
  - اگر مقدار یکی از سه حالت معتبر بود، همان برگردانده می‌شود.
  - در غیر این صورت «auto» → پیش‌فرض کاربران بدون انتخاب قبلی.

خطوط 26-31 resolveMode: در حالت auto، اگر سیستم روشن باشد «light» و
           در غیر این صورت «dark»؛ دو حالت دیگر بدون تغییر برمی‌گردند.

خطوط 33-39 syncButtons: برای هر [data-theme-choice] مقدار aria-pressed را
           با حالت فعلی هم‌گام می‌کند (فقط برای دسترسی‌پذیری؛ ظاهر دکمهٔ
           فعال از data-theme-mode در CSS می‌آید).

خطوط 41-53 fadeTheme: افزودن کلاس theme-fade، اجبار بازچینش با خواندن
           offsetWidth (تا گذار از رنگ فعلی شروع شود) و حذف کلاس پس از
           ۳۲۰ میلی‌ثانیه؛ تایمر قبلی پاک می‌شود تا کلیک‌های سریع تداخل نکنند.

خطوط 55-61 updateMeta: تغییر content متای theme-color به #f6f3ee (روشن)
           یا #080b0e (تاریک) تا نوار مرورگر موبایل هماهنگ بماند.

خطوط 63-76 applyMode(mode, persist):
  - resolved = resolveMode(mode)
  - root.dataset: data-theme = resolved و data-theme-mode = mode
    (اولی رنگ واقعی، دومی انتخاب کاربر).
  - به‌روزرسانی متا و aria-pressed.
  - اگر persist=true، ذخیره در localStorage با try/catch.

خط 78      applyMode(readMode(), false) → اجرای فوری پیش از رندر body.

خطوط 80-88 یک listener کلیک مشترک روی document:
  - target.closest("[data-theme-choice]") → دکمهٔ تم (هر جای صفحه).
  - fadeTheme() سپس applyMode(choice, true) → ذخیرهٔ انتخاب کاربر.
  - استفاده از event delegation یعنی افزودن کلید تم در آینده (مثلاً منوی
    موبایل) بدون تغییر JS کار می‌کند.

خطوط 90-92 پس از DOMContentLoaded، aria-pressed دکمه‌ها با مقدار
           ذخیره‌شده هم‌گام می‌شود.

خطوط 94-104 onSystemChange: اگر حالت فعلی auto باشد و ترجیح سیستم عوض شود،
           تم دوباره اعمال می‌شود (persist=false تا انتخاب کاربر تغییر نکند).
           هم addEventListener و هم addListener قدیمی پشتیبانی می‌شوند.

نکته: اگر JavaScript غیرفعال باشد، HTML با data-theme="dark" رندر می‌شود و
سایت با تم تاریک کار می‌کند؛ فقط امکان تغییر تم وجود ندارد.

۱۰.۱ سطح تهدید
سایت یک بروشور عمومی است: بدون ورود مشتری، بدون سبد خرید، بدون پرداخت و
بدون API عمومی. آپلود فایل فقط از پنل ادمین انجام می‌شود. دارایی‌های مهم:
  1) درخواست‌های استعلام و دادهٔ اعضای باشگاه (نام/تلفن) — حریم خصوصی.
  2) تصاویر محصول و فایل‌های media/ — یکپارچگی و حجم دیسک.
  3) حساب ادمین و پنل مدیریت — کنترل کامل داده و تخفیف‌ها.
  4) اعتبار/دسترس‌پذیری سایت — اسپم فرم می‌تواند دیتابیس را پر کند.

۱۰.۲ کنترل‌های پیاده‌شده و محل آن‌ها
  - XSS: escape پیش‌فرض قالب‌ها؛ نبود safe/mark_safe؛ CSP بدون inline script
    (theme.js هم فایل خارجی محلی است). نام/برند/مشخصات محصول و نام عضو
    باشگاه هم از همین مسیر escape می‌شوند.
  - CSRF: CsrfViewMiddleware + {% csrf_token %} در هر دو فرم + کوکی
    HttpOnly/Secure در تولید.
  - Clickjacking: X-Frame-Options: DENY + frame-ancestors 'none'.
  - MIME sniffing: nosniff.
  - نشت Referrer: same-origin.
  - منابع خارجی: صفر؛ CSP همه را می‌بندد (ضد آلودگی CDN).
  - SQL Injection: ORM جنگو؛ هیچ RawSQL/extra/cursor دستی نیست.
  - اسپم فرم: Honeypot + محدودیت نرخ IP جدا برای استعلام و باشگاه + سقف طول.
  - DoS سبک: محدودیت نرخ؛ اما بدون CAPTCHA/ WAF.
  - آپلود تصویر: فقط کاربر staff از پنل ادمین. فایل با Pillow باز و به WebP
    تبدیل می‌شود؛ فایل خراب خطای ۵۰۰ نمی‌دهد و ذخیره را نمی‌شکند. هیچ
    آپلود عمومی یا مسیر آپلود ناشناس وجود ندارد. نوع فایل با محتوای واقعی
    (نه فقط پسوند) تشخیص داده می‌شود و خروجی همیشه WebP است.
  - دادهٔ باشگاه: فرم عمومی فقط وضعیت «در انتظار تأیید» می‌سازد؛ فعال‌سازی،
    سطح و درصد تخفیف فقط از ادمین قابل تغییر است. فرم عمومی هیچ فیلد
    discount_percent/status ندارد؛ بنابراین کاربر نمی‌تواند تخفیف بگیرد.
    تلفن یکتا و نرمال‌شده است تا ثبت تکراری/دور زدن ساده ممکن نباشد.
  - افشای خطا: DEBUG در تولید خاموش؛ ۵۰۰ قالب سفارشی؛ خطاهای SMTP/کش/تصویر
    فقط لاگ می‌شوند.
  - مدیریت راز: SECRET_KEY از محیط؛ در DEBUG=False اجباری؛ .env در gitignore.
  - پنل: مسیر قابل تغییر؛ رمز با اعتبارسنج‌های استاندارد؛ code/created_at
    readonly؛ حذف محصول فایل‌های media را هم پاک می‌کند.
  - هدرهای اضافی: Permissions-Policy (دوربین/میکروفن/… غیرفعال).
  - پارامترهای GET کاتالوگ: q و brand پیش از استفاده strip و به ۸۰ نویسه
    محدود می‌شوند؛ category و brand فقط از مجموعهٔ مجاز (CATEGORY_CHOICES و
    برندهای واقعی فعال) پذیرفته می‌شوند و مقدار ناشناخته نادیده گرفته می‌شود.
    هیچ ورودی کاربری مستقیم در SQL/queries خام نمی‌رود؛ همه از ORM و
    icontains عبور می‌کنند. در قالب هم مقادیر فیلتر با escape پیش‌فرض چاپ
    می‌شوند.
  - صفحهٔ جزئیات محصول: get_object_or_404 روی Product.objects.filter(

  - اندازهٔ صفحهٔ کاتالوگ: PRODUCTS_PAGE_SIZE سمت سرور با max(6, min(96, n))

    پشتیبان امن بگیرید و در مخزن/لاگ قرار ندهید.
  - اطلاعات تماس و درصدهای نمایشی باشگاه نمونه است؛ قبل از انتشار واقعی شود.
  - مسیر ادمین پیش‌فرض را در تولید تغییر دهید.

۱۲. استقرار در تولید
================================================================================
۱) .env را از .env.example بسازید و مقادیر واقعی بگذارید:
   DJANGO_DEBUG=0
   DJANGO_SECRET_KEY=<64 نویسه تصادفی>
   DJANGO_ALLOWED_HOSTS=example.com,www.example.com
   DJANGO_CSRF_TRUSTED_ORIGINS=https://example.com,https://www.example.com
   DJANGO_ADMIN_PATH=panel-<رشته تصادفی>
   DJANGO_SECURE_SSL_REDIRECT=1
   DJANGO_SECURE_HSTS_SECONDS=31536000
   DJANGO_SECURE_HSTS_PRELOAD=1
   (اگر پشت Nginx/Cloudflare: DJANGO_BEHIND_PROXY=1 و فقط در صورت اطمینان
    DJANGO_TRUST_PROXY_HEADERS=1)

۲) مهاجرت و کاربر:
   python manage.py migrate
   python manage.py createsuperuser
   python manage.py collectstatic --noinput

۳) اجرا با Gunicorn (نمونه):
   gunicorn parstextile.wsgi:application --bind 127.0.0.1:8001 --workers 3

۴) Nginx (نمونهٔ فشرده):
   - server_name example.com
   - listen 443 ssl http2 (گواهی Let’s Encrypt)
   - location /static/ { alias /var/www/parstextile/staticfiles/; expires 30d; }
   - location / { proxy_pass http://127.0.0.1:8001; proxy_set_header Host $host;
                 proxy_set_header X-Forwarded-For $proxy_add_x_forwarded_for;
                 proxy_set_header X-Forwarded-Proto $scheme; }
   - location /media/ { alias /var/www/parstextile/media/; expires 7d;
                        add_header X-Content-Type-Options nosniff;
                        location ~* \.(php|py|pl|sh|html?)$ { deny all; } }
   - client_max_body_size 5m;   # سقف آپلود تصویر در پنل ادمین
   نکته: media/ را هرگز با اجرای CGI/اسکریپت سرو نکنید؛ فقط فایل استاتیک.

۵) PostgreSQL (پیشنهادی):
   pip install "psycopg[binary]" و تغییر DATABASES در settings.py از طریق
   متغیرهای محیطی (در نسخهٔ فعلی فقط SQLite پیکربندی شده است).

۶) کش مشترک برای محدودیت نرخ:
   pip install redis django-redis و تنظیم CACHES روی Redis. دو شمارندهٔ
   استعلام و باشگاه هر دو از همین کش استفاده می‌کنند.

۷) پشتیبان‌گیری: db.sqlite3 (یا دیتابیس PostgreSQL)، پوشهٔ media/ (تصاویر
   اصلی و بندانگشتی‌ها) و .env؛ اجرای دوره‌ای rotate لاگ‌ها.

۸) مجوز فایل‌ها: کاربر وب‌سرور باید در media/products/ و
   media/products/thumbs/ مجوز نوشتن داشته باشد؛ در غیر این صورت آپلود یا
   اکشن «بازسازی بندانگشتی WebP» شکست می‌خورد. پشتیبانی WebP را در سرور
   جدید بررسی کنید:
   python -c "from PIL import features; print(features.check('webp'))"

۹) پایش: لاگ‌های stdout در systemd/Docker؛ هشدار روی خطاهای SMTP، خطای
   پردازش تصویر و ۵۰۰.

- پایش خطا (Sentry) در تولید توصیه می‌شود.
- اطلاعات تماس، آمار و درصدهای نمایشی باشگاه نمونه‌اند و باید واقعی شوند.
- تم در سمت مرورگر و با localStorage مدیریت می‌شود؛ اگر ترجیح تم کاربر باید
  در سرور ذخیره شود (حساب کاربری یا کوکی)، نیازمند طراحی جداگانه است.
- چاپ همیشه با پالت روشن انجام می‌شود و از تم انتخابی کاربر پیروی نمی‌کند.
- دادهٔ باشگاه شخصی است و سیاست نگهداری/حذف آن (مدت نگهداری، درخواست حذف
  مشتری) باید توسط فروشگاه تعریف شود؛ ابزار خودکار حذف/ناشناس‌سازی ندارد.
